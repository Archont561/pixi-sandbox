Three crates, two fixture trees, and one rule about GitHub Actions. This page is the map for
someone who has just cloned the repository and wants to change something.

## Top level

```text
pixi-sandbox/
├── crates/
│   ├── pixi-sandbox-core/     the library: wire format, sharding, verification
│   ├── pixi-sandbox-git/      git behind a trait: real git + an in-memory mock
│   └── pixi-sandbox/          the CLI — and, under tests/fixtures/, the test fixtures
├── docs/                      this site (Astro + Starlight → GitHub Pages), a bun workspace member
├── .github/                   workflows plus verified release/setup/publish Actions
├── .pixi-sandbox.toml         reviewed bundle/platform plan for release-driven publishing
├── .convoco/                  why convoco is deliberately absent
├── package.json               the bun workspace: docs plus repo-wide devDependencies
├── pixi.toml                  environments and every task a human, hook or CI job runs
└── Cargo.toml                 workspace: members, shared dependency versions
```

## The three crates

| crate | responsibility | depends on |
| --- | --- | --- |
| `pixi-sandbox-core` | `manifest.json` (schema 1) and its validation, sharding (`record_file`, `materialise`, atomic `join_parts`), embedded helper-tool pins, publish-plan schema, verification incl. the ELF linkage check | serde, sha2, thiserror, walkdir, toml |
| `pixi-sandbox-git` | `GitProtocol`: `publish`, `fetch_into`, `branch_exists`, `remote_size`. `ShellGit` (real git, swappable `Runner`) and `FakeGit` (in-memory mock) | thiserror |
| `pixi-sandbox` | the CLI (`pack`, `publish`, `restore`, `unpack`, `doctor`, `plan`, `tools`) and the test fixtures | core, git, clap, anyhow |

The split is deliberate: `core` is the part that must be *right* (it decides what reaches a
user's disk), `git` is the part that touches a remote (the part you cannot unit-test against
reality), and the CLI orchestrates verified staging plus external helper tools. All three are
pure Rust, and the static release binaries are the portable bootstrap an airlock restores from.

**Adding a crate** is three steps: `cargo new --lib crates/<name>`, add it to
`members` in the root `Cargo.toml`, and give it `description` plus `license.workspace = true`
— `cargo deny check` fails on a crate without a licence, and it rejects a bare path dependency
(crates that depend on a sibling must state `version` next to `path`). If the crate is part of
the published package, add it to `crates/pixi-sandbox/Cargo.toml` as well; the conda package
(`cargo install`) builds from the workspace, so a missing member shows up as a package that
builds but does not run.

## The fixtures: tests never point at this repository

```text
crates/pixi-sandbox/tests/fixtures/
├── demo-project/     a complete pixi project definition — the *input* to pack
└── transport/        a synthetic, already-packed payload — the *input* to doctor/publish/restore
```

This repository is the tool's own development environment: its `default` environment contains
`pixi-pack`, and its lockfile resolves hundreds of MiB. A test pointed at the repository root
would therefore test the developer's machine — passing where a fresh clone fails, slow, and
blind to the bugs that only appear on a plain project. So:

- `demo-project/` has **no** `pixi-pack`/`pixi-unpack` dependency, and a test asserts that;
- `transport/` is a committed 15 KB payload with real digests, including a blob split into
  `.partNNN` parts, so the verification path runs without pixi, a packer or a network;
- tests copy a fixture into a temp directory before writing to it;
- a test that walks out of its crate from `CARGO_MANIFEST_DIR` fails the suite.

Measured bonus: the fixture project is **packable without installing its environment** —
`pixi-pack` resolves from `pixi.lock` — so pack-integration tests need network but not a
multi-GiB local install (485 blobs / 100.6 MiB / 2.2 s).

## GitHub Actions: source-driven commands stay one line

Source-driven commands in `.github/workflows/` are `pixi run <task>`. If one needs
more than one line, it becomes a task in `pixi.toml` — not inline bash. The release-driven
publisher uses auditable composite actions in bash/pwsh with checksum verification:

- the command CI runs is the command you run locally, so a red gate reproduces in one paste;
- logic is diffable and shell-independent (the Windows runner defaults to `pwsh`);
- the workflow reads like the list of gates it is.

```yaml
      - uses: actions/checkout@11d5960a326750d5838078e36cf38b85af677262 # v4
      - uses: prefix-dev/setup-pixi@ba3bb36eb2066252b2363392b7739741bb777659 # v0.8.1
        with: { environments: default, cache: true }
      - run: pixi run sandbox-pack . default "$TRANSPORT" linux-64   # pack + vendor + pinned tools
      - run: pixi run sandbox-doctor "$TRANSPORT"                     # verify every blob, write nothing
      - run: pixi run sandbox-publish "$BRANCH" origin "$TRANSPORT"   # one orphan commit, force-pushed
```

The unified `publish-sandbox.yml` workflow (replaces `publish-sandbox` + `publish-sandboxes`) validates
`.pixi-sandbox.toml` via `plan --json`, then for each native bundle/platform calls `setup-pixi-sandbox`
to verify a release and `publish-pixi-sandbox` composite to pack/doctor/publish. All third-party
workflow dependencies are full-SHA pins; release-label comments are informational only.

Paths come from the environment: pixi tasks expand `$VAR` but do **not** support
`${VAR:-default}`, so the local tasks carry literal defaults and the `ci-*` tasks read
`SANDBOX_PROJECT`, `SANDBOX_ENVS`, `SANDBOX_TRANSPORT`, `SANDBOX_PLATFORM`, `SANDBOX_BRANCH`,
`SANDBOX_REMOTE`, `SANDBOX_SELF_BIN`, `SANDBOX_CARGO_VENDOR` and `SANDBOX_PROOF_OUT` — all set
in the workflow's `env:` block.

## What is never committed

`.pixi/`, `target/`, `vendor/`, `.pixi-sandbox/`, `node_modules/`, `docs/dist/` and
`.sandbox-*`. The payload lives on the sandbox branch; the crate sources are vendored on
demand; a fixture that grows past a quarter of a MiB fails a test.

## Working on pixi-sandbox itself

Clone and run the suite — it includes the fixture-backed
doctor → publish → network-isolated restore lifecycle (on Linux the e2e suite re-runs the
restore inside `unshare -rn`):

```bash
git clone https://github.com/Archont561/pixi-sandbox && cd pixi-sandbox
pixi run --frozen test
pixi run --frozen lint
```

Every task goes through the pixi binary — never bare `cargo`, `bun`, or `taplo`. The command CI
runs is the command you run locally, so a red gate reproduces in one paste.

## Shipping the tool

The package is a conda package built from the workspace. The task runs in the empty `package`
environment — which is how the release matrix builds one variant per native runner, `win-64`
included:

```bash
pixi run -e package package                        # build the variant for this runner
pixi run -e package xtask smoke-conda-package      # its smoke test, same environment
```

The canonical install is the ecosystem channel:

```bash
pixi global install -c https://prefix.dev/archont561/archont561 -c conda-forge pixi-sandbox
```

Measured: 34s to build a 594 KB package (1.26 MiB stripped binary); the channel write produces
`repodata.json` + `.zst` + sharded repodata, so a plain static host works as a channel. Always
combine with `-c conda-forge`.

## Editing this documentation

The site is Astro + Starlight under `docs/`, a bun workspace member. Build it with
`pixi run docs build` (or `bun run build` inside `docs/`); the site never carries a literal release
tag — the config substitutes `__VERSION__` from the workspace manifest, so a release commit
rewrites zero documentation lines. Pages are MDX in `docs/src/content/docs/`, organized by the
role/lifecycle IA: propose structural changes as a backlog task first, and keep the airlock page
actionable for someone with no network and no context.

### The guide template

Every page under `guides/` — and the operator pages that share their shape, `restore.mdx` and
`first-offline-bundle.mdx` — opens and closes the same way, so a reader always knows where they
are and what the page will ask of them:

- **Opens with** a `GuideMeta` box (`docs/src/components/GuideMeta.astro`, imported from the
  page): the **outcome**, the **audience**, the **prerequisites**, the **machine context**
  (the same connected/airlock vocabulary the context chips use), and the **maturity** of the
  feature. Values may be inline JSX, so `<code>` and links work inside the box.
- **Body** carries the how, in lifecycle order.
- **Closes with** three sections, in this order and under these exact headings:
  `## Verification` (how to prove the outcome), `## Failure modes` (the symptom, linking the
  matching [Troubleshooting](/pixi-sandbox/troubleshooting/) entry), and `## Next steps`
  (the next safe action in the lifecycle, naming its prerequisite).
- `restore.mdx` is the reference implementation: its printable operator checklist sits directly
  under the meta box, and the page still ends with the three closing sections.

A new guide is not done until its `Next steps` names the next lifecycle stage and that stage's
prerequisite — the pages form a chain, not a set.

### Docs quality gates

`.github/workflows/docs.yml` runs four gates before the site is published, and each is a `pixi
run` task you can run locally — the gate is the same gate in CI and on a laptop:

| Task | What it proves |
|---|---|
| `pixi run docs-frontmatter-check` | No page's `title:`/`description:` breaks Starlight's YAML parser |
| `pixi run docs-link-check` | Every internal link and fragment in the built site resolves |
| `pixi run docs-a11y-check` | Structure (one `h1`, no skipped levels, alt text, accessible names, table headers, skip link), `:focus-visible` rules, print rules, the operator checklist's script-free markup, and WCAG contrast ratios for the site's color pairs in **both** themes |
| `pixi run docs-snippet-check` | Every `pixi-sandbox …` command the docs tell a reader to run exists, and every documented flag is one the binary accepts (it builds the CLI with `cargo` when needed) |

The browser-dependent half of the audit is a protocol, run by hand after a visual change and
recorded in the pull request:

- **Keyboard** — Tab from the address bar through the sidebar groups, the search button, the
  theme control, and every code block's copy button; Enter/Space activate; Esc closes search.
  Focus must be visible at every stop, in **both** themes.
- **Responsive** — 375 px (single column, ToC collapses), 768 px (the transport diagram
  stacks), 1280 and 1440 px (reference pages use their wider content mode; wide tables and
  TOML blocks do not wrap excessively).
- **Print and no JavaScript** — print the restore page: the operator checklist must stay on one
  page with its tick boxes, and reload that page with JavaScript disabled: the checklist and
  every command block must still be complete and static.

Two things the automated gate deliberately does not cover: the badge strip on the homepage is
third-party imagery from shields.io (contrast there is their design, checked by eye), and the
keyboard walk above needs a real browser.

### Icons and the docs design system

Icons render through [Astro Icon](https://www.astroicon.dev/) over
[Iconify](https://iconify.design/): one import — `import { Icon } from 'astro-icon/components';` —
and one call, `<Icon aria-hidden="true" name="set:name" size={n} />`. The bundled sets are `lucide`, `mdi`,
`tabler`, and `simple-icons` (all of each, declared in `docs/astro.config.mjs`); browse them at
[icon-sets.iconify.design](https://icon-sets.iconify.design/) before reaching for a new
dependency. Astro Icon emits the SVGs `aria-hidden`, so an icon never carries meaning on its own —
pair it with a text label or a heading.
