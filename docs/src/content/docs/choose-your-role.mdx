pixi-sandbox is never used by one person on one machine. A transport exists because a
**connected** side produces it and an **airlocked** side consumes it — and usually a CI system
publishes in between. Pick the role that matches what you are here to do; each card links the
first page of that role's path.

## I am a project owner

<div style="display: flex; gap: 0.75rem; padding: 1rem; background: var(--sl-color-gray-6); border-radius: 0.5rem; margin-bottom: 1rem;">
  <Icon name="lucide:user" size={20} />
  <div>
    <strong>You configure the bundle and commit the generated assets.</strong>
    <p style="margin: 0.25rem 0 0; color: var(--sl-color-gray-2); font-size: 0.9rem;">Your project has <code>pixi.toml</code> + <code>pixi.lock</code> and you want its environments on machines that have no network. You work on the connected host.</p>
  </div>
</div>

**Your path:**

1. [Install and verify the CLI](/pixi-sandbox/installation/)
2. [First verified offline bundle](/pixi-sandbox/first-offline-bundle/) — one documented project, end to end
3. [Configure bundles](/pixi-sandbox/guides/configure-bundles/) — environments, platforms, launchers
4. [Cargo vendoring](/pixi-sandbox/guides/cargo-vendoring/) — when you need crates on the far side
5. [Transport sizes, sharding, and budgets](/pixi-sandbox/guides/sizes-and-budgets/) — keep the branch pushable

**The mistake to avoid:** packing a `pixi global install` launcher as the transport's embedded
binary. Pack the checksum-verified release asset or a binary you built — see
[Configure bundles](/pixi-sandbox/guides/configure-bundles/).

## I am a CI maintainer

<div style="display: flex; gap: 0.75rem; padding: 1rem; background: var(--sl-color-gray-6); border-radius: 0.5rem; margin-bottom: 1rem;">
  <Icon name="lucide:bot" size={20} />
  <div>
    <strong>You publish safely and keep workflow policy current.</strong>
    <p style="margin: 0.25rem 0 0; color: var(--sl-color-gray-2); font-size: 0.9rem;">You own <code>.github/workflows/publish-sandbox.yml</code>: the matrix, the permissions, the failure surfaces, and the upgrade lane that keeps generated files fresh.</p>
  </div>
</div>

**Your path:**

1. [CI publishing](/pixi-sandbox/guides/ci-publishing/) — the generated publisher, end to end
2. [Generated workflow policy](/pixi-sandbox/guides/workflow-policy/) — carry policy in config, never hand edits
3. [Migration from composite Actions](/pixi-sandbox/guides/migration/) — if your project still calls the retired Actions
4. [Diagnostics and evidence logs](/pixi-sandbox/security/diagnostics/) — what to collect when a publish leg fails

**The mistake to avoid:** hand-editing the generated workflow. It is regenerated by `init` from
`pixi-sandbox.toml`; edits outside the `[workflow]` table are silently reverted by the next
regeneration.

## I am an airlock operator

<div style="display: flex; gap: 0.75rem; padding: 1rem; background: var(--sl-color-gray-6); border-radius: 0.5rem; margin-bottom: 1rem;">
  <Icon name="lucide:shield-check" size={20} />
  <div>
    <strong>You verify and restore locally, with zero network.</strong>
    <p style="margin: 0.25rem 0 0; color: var(--sl-color-gray-2); font-size: 0.9rem;">You stand in front of the disconnected machine. Nothing you run may reach the internet; if anything tries, stop and report it.</p>
  </div>
</div>

**Your path:**

1. [Restore on the airlock](/pixi-sandbox/restore/) — the checklist and the one-command restore
2. [Troubleshooting and incident response](/pixi-sandbox/troubleshooting/) — symptom-first recovery
3. [Diagnostics and evidence logs](/pixi-sandbox/security/diagnostics/) — evidence you can transfer back

**The mistake to avoid:** letting `pixi install --frozen --offline` "fix" a drifted environment.
If it starts doing real work, the tree does not match the lockfile — re-run the restore instead.

## I am a security or platform reviewer

<div style="display: flex; gap: 0.75rem; padding: 1rem; background: var(--sl-color-gray-6); border-radius: 0.5rem; margin-bottom: 1rem;">
  <Icon name="lucide:lock" size={20} />
  <div>
    <strong>You evaluate the guarantees, the constraints, and the host boundary.</strong>
    <p style="margin: 0.25rem 0 0; color: var(--sl-color-gray-2); font-size: 0.9rem;">You need to know exactly what is verified, what the transport proves, what it deliberately does not do, and what the host must provide.</p>
  </div>
</div>

**Your path:**

1. [Verification guarantees](/pixi-sandbox/security/verification-guarantees/) — integrity model and threat boundaries
2. [Host and GUI requirements](/pixi-sandbox/security/host-requirements/) — the machine half of the contract
3. [Diagnostics and evidence logs](/pixi-sandbox/security/diagnostics/) — what is logged, and what is redacted
4. [Transport sizes, sharding, and budgets](/pixi-sandbox/guides/sizes-and-budgets/) — ceilings enforced before a push

**The boundary to remember:** unpacking runs package post-link scripts — code from the bundle
executes on your machine. That is inherent to conda environments; protect the branch accordingly.
