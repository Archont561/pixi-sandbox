pixi-sandbox is a two-sided tool. One side has a network; the other side must never need one.
Everything in the documentation hangs off that split, so this page defines it once: the lifecycle,
what lives on each machine, what crosses the gap, and what is proven at every step.

## What exists on each machine

| | Connected host | Airlock |
|---|---|---|
| Network | Yes — prefix.dev, crates.io index, GitHub | None. If anything reaches out, stop. |
| pixi-sandbox | Installed (canonical channel package or verified release binary) | Not required — the transport carries its own verified copy |
| Pixi | Required (drives `pack`) | Required only to *run* the project; registered by the restore |
| Git | Required (publishes the branch) | Required (clone/bundle + `git archive`) |
| Writes | `pixi-sandbox.toml`, workflows, launchers | `.pixi/envs/*`, vendored crates, registered user tools |

## What crosses the air gap

The orphan branch and nothing else. Its root carries Markdown only; the payload lives under
`.pixi-sandbox/`:

```text
sandbox/developer-linux-64 (orphan branch)
├── .pixi-sandbox/
│   ├── manifest.json              # SHA-256 catalog, source commit, tool versions
│   ├── envs/<env>/pack/           # pixi-pack --directory-only output
│   ├── tools/<platform>/          # pixi, pixi-pack, pixi-unpack, pixi-sandbox (static, verified)
│   └── vendor/                    # cargo vendor tree (when vendoring is enabled)
├── README.md                      # human restore instructions
└── AGENTS.md                      # agent instructions
```

Credentials never cross: the transport authenticates to nothing, and diagnostic logs are
redacted before they are written. See [Verification guarantees](/pixi-sandbox/security/verification-guarantees/).

## What is verified, and when

| Check | Runs | Writes |
|---|---|---|
| SHA-256 of every blob against `manifest.json` | `doctor --verify`, and again inside `restore` before any write | nothing |
| Standalone probe of the embedded binary | `doctor --verify` (after a green hash report) | nothing |
| Per-file oracle of the restored tree | `doctor --verify-restored` | nothing |
| Budget ceilings | `doctor --budget-config`, before `publish` force-pushes | nothing |
| Offline no-op assertions | after `restore` completes | the project prefix |

## Which files are generated or committed

`pixi-sandbox init` owns exactly these files, each carrying a `pixi-sandbox-version` marker and
regenerable with `init --force` (or audited read-only with `init --check`):

```text
pixi-sandbox.toml                      # reviewed bundle/platform plan (created if absent)
.github/workflows/publish-sandbox.yml  # project-owned publisher
.github/workflows/relock.yml           # lockfile refresh bot
restore.sh  (or restore.ps1)           # the one airlock-side entrypoint
```

Your `pixi.toml` is never modified — the CLI is installed globally with an explicit channel, so
the project's channel list never needs to know where it came from.
