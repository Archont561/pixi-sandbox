This page is written for the person (or agent) standing in front of the disconnected
machine. Nothing here needs network access — if any step tries to reach out, stop and
report it. Terms used here (transport, sandbox branch, doctor, manifest) are defined once in
the [Glossary and security boundaries](/pixi-sandbox/glossary/).

If a step fails, stop and find the symptom in
[Troubleshooting and incident response](/pixi-sandbox/troubleshooting/) — it is organized by what
you see, not by command.

## 1. Get the branch

<div style="display: flex; gap: 0.5rem; align-items: center; margin-bottom: 0.75rem;">
  <Icon aria-hidden="true" name="lucide:git-branch" size={18} />
  <strong>Fetch orphan branch</strong>
</div>

<ContextChips chips={["connected", "network"]} />

```bash
# on the connected host, include both refs in the transferred Git bundle
git bundle create project-airlock.bundle main sandbox/dev-linux-64
```

The sandbox branch carries its static tooling under `.pixi-sandbox/tools/<platform>/`; its root
contains Markdown only. A transfer that [lacks the branch](/pixi-sandbox/troubleshooting/#3-the-sandbox-branch-is-not-in-the-transfer-bundle)
fails here, not at the restore. The normal project branch carries the minimal launchers generated by
`pixi-sandbox init`.

<div style="display: flex; gap: 0.5rem; align-items: center; margin: 1rem 0; padding: 0.75rem; background: var(--sl-color-accent-low); border-radius: 0.5rem;">
  <Icon aria-hidden="true" name="lucide:zap" size={18} />
  <span><strong>One-command offline reconstruction</strong></span>
</div>

<ContextChips chips={["airlock", "offline"]} />

```bash
git clone project-airlock.bundle project
cd project
./restore.sh              # Linux/macOS
# .\\restore.ps1         # Windows
```

The launcher resolves its branch from the config selected by `init` (`pixi-sandbox.toml` is
preferred and `.pixi-sandbox.toml` is the compatibility fallback), derives
`<branch_prefix>/<bundle>-<platform>` for the host, calls `git archive`, extracts into
project-local scratch, and invokes the verified nested binary. When a connected clone lacks the
sandbox ref, it fetches that one branch into `origin/<branch>`; set `PIXI_SANDBOX_FETCH=skip` to
require local Git objects only. Set `PIXI_SANDBOX_BRANCH` to pin an exact branch, or
`PIXI_SANDBOX_BUNDLE` to choose between bundles that cover the same platform.

## 2. Look before you leap

<div style="display: flex; gap: 0.5rem; align-items: center; margin-bottom: 0.75rem;">
  <Icon aria-hidden="true" name="lucide:shield-check" size={18} />
  <strong>Verify every byte</strong>
</div>

<ContextChips chips={["airlock", "offline", "readonly"]} />

```bash
/tmp/sb/.pixi-sandbox/tools/linux-64/pixi-sandbox doctor \
    --branch-location /tmp/sb --verify
```

This checks every sha256 in `manifest.json` and reports the payload breakdown. It writes
nothing. Treat any failure as a hard stop — a [digest mismatch](/pixi-sandbox/troubleshooting/#2-doctor-found-a-digest-mismatch)
or an embedded binary that [cannot execute](/pixi-sandbox/troubleshooting/#4-restore-cannot-execute-the-embedded-binary)
has its own recovery path.

### Keep evidence when the primary log is unreachable

If an Actions or operator log cannot cross the airlock boundary, ask the connected side to rerun
`pack`, `doctor`, or `publish` with a fresh `--log-file <PATH>`. The file is flushed after every
phase and includes the complete causal error chain on failure; `-v` mirrors phase names to stderr
and `-vv` adds reviewed non-secret context. Transfer that bounded text file beside the incident
report, **not inside the transport branch**. Never reuse its path: pixi-sandbox refuses to
overwrite an existing diagnostic log so the first failure is not silently destroyed. Remote
credentials and common token/password query values are not recorded.

For a local airlock check, the same binary can write evidence without changing doctor’s normal
report:

<ContextChips chips={["airlock", "offline", "readonly"]} />

```bash
/tmp/sb/.pixi-sandbox/tools/linux-64/pixi-sandbox doctor \
    --branch-location /tmp/sb --verify \
    --log-file /path/to/new/doctor-attempt.log
```

## 3. Restore

<div style="display: flex; gap: 0.5rem; align-items: center; margin-bottom: 0.75rem;">
  <Icon aria-hidden="true" name="lucide:package-check" size={18} />
  <strong>Materialize environments</strong>
</div>

<ContextChips chips={["airlock", "offline"]} />

```bash
cd /path/to/project
/tmp/sb/.pixi-sandbox/tools/linux-64/pixi-sandbox restore \
    --branch-location /tmp/sb \
    --output-path . --force
```

What it does, in order: verifies the tools, stages a copy of each pack under a work dir on
the project's filesystem, installs format-1 packages using native rattler/UV libraries, writes
final-prefix markers and verifies the staged file oracle before promoting each environment to
`.pixi/envs/<env>`, materialises the vendored crates, writes
Cargo source replacement to sandbox-owned `.pixi-sandbox/cargo-home/config.toml`, adds
per-environment Pixi/Conda activation hooks that set `CARGO_HOME`, removes any legacy
`.pixi/sandbox-env.sh`, verifies the restored tree against the manifest's per-file digests, and
— only after that verification — registers the user tools (below).

For a self-bootstrapping transport, the producer must explicitly bundle Pixi and the standalone
bootstrap with `--pixi-bin` and `--self-bin`. Registration applies only to executables actually
recorded in the manifest. Legacy opaque packs retain their recorded unpacker compatibility path;
format-1 restoration does not require an external helper.

There is one supported package-command entrypoint after restore: **pixi**. A verified restore puts small
managed launchers for `pixi` and `pixi-sandbox` into `~/.local/bin` (Windows:
`%USERPROFILE%\.pixi-sandbox\bin`) and adds that directory to your shell profile's `PATH`
(Windows: the user `PATH` in the registry — no administrator rights). In a **new** shell,
`pixi` and `pixi sandbox` then work directly; pixi discovers `pixi sandbox` by finding
`pixi-sandbox` on `PATH`, which is why both are registered. The launchers `exec` the
manifest-verified copies under `<project>/.pixi/tools/<platform>/` and carry a
`managed by pixi-sandbox` marker; restoring another project retargets them, so the most
recently registered restore is the user-level tool source. An already-running shell cannot be
mutated — open a new one, or run the `export PATH=...` line the restore prints.

No project-level activation script is generated or supported. Do not source
`.pixi/sandbox-env.sh` and do not run bare `cargo`, `rustc`, or `bun` from a restored prefix;
use `pixi run ...` so pixi selects the environment, loads the restore-owned Cargo activation
hook, and keeps the lockfile/offline contract visible.

Registration refuses to overwrite a `pixi` or `pixi-sandbox` you already have in the user bin
directory unless you pass `--force`. For CI runners, shared accounts, or locked-down airlocks,
set `PIXI_SANDBOX_USER_TOOLS=skip` before running the generated launcher (or append
`--user-tools skip` when you call `pixi-sandbox restore` yourself and know the binary
understands it): restore then touches nothing outside the project, and verification and
project output are identical either way. The generated launchers pass the policy as an
environment variable rather than a flag on purpose — the binary a launcher executes comes
from the packed branch, which may predate the flag, and an unknown variable is ignored where
an unknown flag is a hard error. `--user-bin <dir>` relocates the launchers for sites with
their own bin-directory policy.

Native installation links packages for the eventual destination prefix, handling the package's
text/binary prefix metadata before promotion. The legacy unpacker path additionally relocates
textual staging-prefix references. The staged file oracle is checked before an existing prefix
can be retired. And on success the work dir is removed: a completed restore leaves no scratch behind. A
**failed** restore keeps it, because that is where the partial materialisation is worth looking at.

:::caution[Never use a small `/tmp` as the work dir]
Restoration needs scratch for materialized archives, package caches and staged prefixes. A
small tmpfs `/tmp` can exhaust space; promotion also requires the destination filesystem. The default work dir is
`<project>/.pixi/.restore-work`; override it with `--work-dir` if the project lives on a
small volume.
:::

## 4. Prove it is offline-clean

<div style="display: flex; gap: 0.5rem; align-items: center; margin-bottom: 0.75rem;">
  <Icon aria-hidden="true" name="lucide:check-circle" size={18} />
  <strong>Offline assertions</strong>
</div>

<ContextChips chips={["airlock", "offline"]} />

```bash
pixi install --frozen --offline                 # must be a no-op, must not touch the network
pixi run --frozen -- cargo build --offline      # uses the vendored crates only
```

In a *new* shell, plain `pixi` and `pixi sandbox` resolve through the registered user tools. If
registration was skipped, call the manifest-owned binary explicitly:
`./.pixi/tools/<platform>/pixi run --frozen <task>`.

If `pixi install --frozen --offline` starts doing real work, the environment on disk does
not match `pixi.lock` — do not let it continue; re-run the restore instead. A Rust project whose
[cargo build still fetches](/pixi-sandbox/troubleshooting/#8-vendored-cargo-build-still-fetches) has
the same shape of drift. If your project
already tracks `.cargo/config.toml` for aliases, rustflags, target runners, or `[env]`, the
default restore leaves it byte-for-byte intact; Cargo's vendor replacement lives in
`.pixi-sandbox/cargo-home/config.toml` and is selected by Pixi's environment activation.

## Post-link scripts

Unpacking runs package post-link scripts, i.e. code from the bundle executes on your
machine. That is inherent to conda environments — the bundle is signed/verified content and
the branch should be protected accordingly. Ask for `--verify-only` runs and signed
manifests if your site requires it.

## Verification

Section 4 above is the verification, and it is the last thing you do: `pixi install --frozen
--offline` must be a no-op, `pixi run --frozen -- cargo build --offline` must build from the
vendored crates only, and the registered user tools must resolve in a new shell. A restore is not
proven until all three hold — if the install starts doing real work, re-run the restore rather
than letting it continue.

## Failure modes

Every failure is a hard stop, and each symptom has its own recovery path in
[Troubleshooting and incident response](/pixi-sandbox/troubleshooting/):

| What you see | Entry |
|---|---|
| A restore step reaches for the network | entry 1 |
| `doctor --verify` reports a digest mismatch | entry 2 |
| The sandbox branch is not in the transferred bundle | entry 3 |
| The embedded binary cannot execute | entry 4 |
| The host rejects an object as too large | entry 5 |
| A missing GUI, font, or display server | entry 6 |
| `cargo build --offline` still fetches | entry 8 |

When an Actions or operator log cannot cross the boundary, ask the connected side to re-run the
failing phase with a fresh `--log-file <PATH>` and transfer that bounded file beside the incident
report — [Diagnostics and evidence logs](/pixi-sandbox/security/diagnostics/) is the collection
procedure, and "Filing an incident" is the last section of the troubleshooting page.

## Next steps

**Run the workload** — with the offline assertions green, the restore is done: `pixi run --frozen
<task>` in a new shell. When something failed instead, the next safe action is the symptom entry
above, then [Filing an incident](/pixi-sandbox/troubleshooting/#filing-an-incident). Related:
