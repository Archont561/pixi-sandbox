## The two product commands

Run the first command from the root of your Pixi project on the **connected side**:

Connected hosts need Pixi installed. Install the native package from the canonical channel, then initialise:

<ContextChips chips={["connected", "network"]} />

```bash
pixi global install --channel https://prefix.dev/archont561/archont561 --channel conda-forge pixi-sandbox
pixi-sandbox init
```

`pixi-sandbox init` creates the preferred `pixi-sandbox.toml`, the GitHub workflow, and exactly one launcher for
the connected host:

```text
pixi-sandbox.toml
.github/workflows/publish-sandbox.yml
restore.sh          # Linux/macOS
# restore.ps1       # Windows instead
```

Review and commit those files. Existing projects that carry `.pixi-sandbox.toml` keep using it;
an explicit `--config PATH` wins over both conventional names. Pushing the project runs the generated workflow and publishes the
configured `sandbox/<bundle>-<platform>` branches. Transfer Git history containing the project and
sandbox branch into the disconnected network. On the **airlock**, the second product command is:

<ContextChips chips={["airlock", "offline"]} />

```bash
./restore.sh
```

That script only uses local Git objects: it archives the platform's sandbox branch, locates the
verified nested binary, and restores everything offline. It never contacts GitHub. Windows users
run `.\\restore.ps1` instead.

> The Git push, workflow completion, and transfer across the air gap are deployment operations,
> not additional pixi-sandbox commands. The airlock clone must contain the sandbox branch.

### Use a mirror

Configure Pixi's channel or mirror settings before running the canonical install command when your organisation proxies prefix.dev.

## 1. Prerequisites

- Your project has `pixi.toml` + `pixi.lock`
- Optional: `Cargo.toml` + `Cargo.lock` if you want vendored crates
- On the connected host: Pixi and Git
- On the airlock: Git and `tar`; Pixi and `pixi-sandbox` do not need to be installed

The connected host installs `pixi-sandbox` from the signed native package channel. Standalone release binaries and `SHA256SUMS` remain available for verified transport bootstrap.

## 2. Decide what to ship

Not every env in `pixi.toml` should be an airlock branch. Declare explicitly in `pixi-sandbox.toml`:

```toml
# pixi-sandbox.toml
schema = 1
branch_prefix = "sandbox"
cargo_vendor = true  # false if you only need conda envs

[[bundle]]
name = "developer"
environments = ["dev", "docs"]
platforms = ["linux-64", "osx-arm64", "win-64"]

[[bundle]]
name = "minimal"
environments = ["default"]
platforms = ["linux-64"]
cargo_vendor = false
```

Validate:

<ContextChips chips={["connected"]} />

```bash
pixi-sandbox plan --config pixi-sandbox.toml
pixi-sandbox plan --config pixi-sandbox.toml --json
```

This emits a GitHub Actions matrix — one job per `bundle × platform`.

### Nested Pixi workspaces (schema 2)

A repository whose root tasks delegate to subprojects (`pixi run --manifest-path subproject/pixi.toml …`)
needs those subprojects' environments restored too, or the delegated task re-solves and fetches on a
machine that cannot reach a channel. Declare them explicitly:

```toml
# pixi-sandbox.toml
schema = 2

[[bundle]]
name = "developer"
environments = ["default"]
platforms = ["linux-64"]

[[bundle.workspaces]]
manifest = "subproject/pixi.toml"   # the nested project's lock and prefix
environments = ["default"]          # optional; omitted means that project's `default`
```

Nothing is discovered. The list is reviewed configuration, because subprojects commonly pin
conflicting versions, channels or platforms on purpose — a scan would carry whatever it found and
call it a decision.

`plan` names every declared workspace, its environments, how many packages its lock resolves, the
size those artifacts add, the channels its lock records and the resolved package identities:

```bash
pixi-sandbox plan --config pixi-sandbox.toml
#   workspace subproject: subproject/pixi.toml · default · 42 package(s) · 380 MiB · bundle developer · channels: conda-forge,file:///mirror · set: numpy==2.1.1=py312h...,requests==2.32.3=pyhd8ed1ab_0
```

and `plan --json` carries the same data under `workspaces` (`channels` and `identities`, both
de-duplicated and sorted; either key is omitted when empty, and the text line then prints `-`).
The workflow matrix still comes from `include` alone.

A nested workspace is **not** required to agree with the root about channels or package versions:
each workspace keeps its own lock and its own prefix, so pinning different versions is the point
of declaring it separately rather than merging manifests. That divergence is surfaced in the
plan above for review, not refused. What is refused is anything that would make a restore
ambiguous — the structural cases in the table below.

A nested workspace that holds its own `Cargo.lock` is vendored independently when
`cargo_vendor` is enabled: one complete tree per project, carried in the same transport under
`vendor/workspaces/<slug>/`, restored to that workspace's own `.pixi-sandbox/vendor/`. The plan
text and `plan --json` report a `vendor_crates` count for every workspace that owns a lock, and
when two lockfiles pin the same crate+version the pack output and pack README name the shared
crates and bytes as a vendor overlap — both copies still travel, because there is no
cross-workspace dedup. See [Cargo vendoring](/pixi-sandbox/guides/cargo-vendoring/) for the
layout and the offline build contract.

**What is refused, and why:**

| Declaration | Refusal |
| --- | --- |
| a path outside the repository, or a `.`/`..` component | the value ends up in a join on the consumer's machine |
| a file that is not a `pixi.toml`, or the repository root's own | the root's environments are declared by `environments` |
| the same manifest in two bundles | two branches would restore over one prefix |
| a nested workspace with no `pixi.lock` | pack would fail after the root environments were already packed |
| a root environment named `workspaces` | that is the transport segment nested environments live under |
| a nested manifest missing a platform the bundle publishes, or a lock that cannot resolve the selected environment | the matrix job would fail on the runner |

Packing takes the same `<workspace>/<env>` ids as restoring:

```bash
pixi-sandbox pack --repo-root . --config pixi-sandbox.toml \
  --envs default,subproject/default --platform linux-64 --output-dir .sandbox-out
```

Each environment is resolved to **its own project root** for its lock, its preflight and its
per-file oracle. Inside the transport, the root environment keeps the layout it always had
(`.pixi-sandbox/envs/<env>/pack/…`) and nested ones sit under one fixed segment
(`.pixi-sandbox/envs/workspaces/<slug>/<env>/pack/…`), where `<slug>` is the declared directory
with `/` folded to `-` (`tools/py` → `tools-py`). Restore puts the root environment back in
`.pixi/envs/<env>` and each nested one in **its own project's** `.pixi/envs/<env>` — the layout
`pixi run --manifest-path …` reads, which is what makes the delegated task offline.

Transport manifests written by this build are **schema 4** whether or not a bundle declares a
nested workspace, so there is one writer path rather than two. Readers still accept schemas 1–3;
a consumer on a schema-3-era binary must upgrade before it can read a transport packed after this
change.

## 3. Local pack → doctor → publish

<Tabs>
  <TabItem label="Rust self-bin (recommended)">
    <ContextChips chips={["connected"]} />

    ```bash
    # Build static self-binary
    cargo build -p pixi-sandbox --release
    ```

    <ContextChips chips={["connected"]} />

    ```bash
    # Pack: locked artifacts + vendored crates + explicit executables
    pixi-sandbox pack \
      --repo-root . \
      --envs dev,docs \
      --output-dir .sandbox-out \
      --platform linux-64 \
      --cargo-vendor \
      --pixi-bin pixi \
      --self-bin target/release/pixi-sandbox
    ```

    <ContextChips chips={["connected", "readonly"]} />

    ```bash
    # Verify (writes nothing)
    pixi-sandbox doctor --branch-location .sandbox-out --verify
    ```

    <ContextChips chips={["connected", "network"]} />

    ```bash
    # Publish as the orphan branch
    pixi-sandbox publish \
      --input-dir .sandbox-out \
      --branch-name sandbox/developer-linux-64 \
      --remote origin
    ```
  </TabItem>
  <TabItem label="Release binary">
    <ContextChips chips={["connected"]} />

    ```bash
    # Download verified release
    # (use setup action in CI, or manual curl + sha256sum check)

    pixi-sandbox pack \
      --repo-root . \
      --envs dev \
      --output-dir .sandbox-out \
      --platform linux-64 \
      --pixi-bin pixi \
      --self-bin ./pixi-sandbox-x86_64-unknown-linux-musl
    ```
  </TabItem>
</Tabs>

> **Never pack `$(command -v pixi-sandbox)`.** Installed with `pixi global install`, that
> path is a *launcher trampoline*, not the standalone binary: it looks for
> `trampoline_configuration/pixi-sandbox.json` beside the executable, which only exists in
> the global prefix — so the packed branch passes every hash check and then dies at restore
> with `Couldn't open "…/trampoline_configuration/pixi-sandbox.json"` (issue #81). Pack
> probes `--self-bin` by executing it under an empty environment and refuses such files;
> `doctor --verify` applies the same check to a transport before anyone restores it. The
> only correct sources are the release asset (`pixi-sandbox-<target>`, verified against the
> release's `SHA256SUMS`) or a binary you built yourself.

## 4. What gets published?

```text
sandbox/developer-linux-64 (orphan branch)
├── .pixi-sandbox/
│   ├── manifest.json              # SHA-256 catalog, source commit, tool versions
│   ├── envs/dev/pack/             # native format-1 channel and wheels
│   │   ├── channel/linux-64/*.conda
│   │   ├── environment.yml
│   │   └── pixi-pack.json
│   ├── envs/docs/pack/            # second env, shared .conda files deduped by git
│   ├── tools/linux-64/            # explicitly selected pixi / standalone pixi-sandbox
│   └── vendor/                    # cargo vendor --versioned-dirs (if enabled)
├── README.md                      # human restore instructions
└── AGENTS.md                      # agent instructions
```

Sizes depend on the environment set, the crates, and the tools. The measured breakdown, the
sharding mechanism, and the pre-push budgets are in
[Transport sizes, sharding, and budgets](/pixi-sandbox/guides/sizes-and-budgets/).

## 5. Restore on airlock

After the project and its sandbox branch have crossed the air gap:

```bash
./restore.sh
```

The generated script reads `pixi-sandbox.toml` and selects
`<branch_prefix>/<bundle>-<platform>` for the native platform — the same name
`pixi-sandbox plan` gives the publisher, so renaming a bundle or prefix needs no regenerated
launcher. It then uses `git archive` into `.pixi/.restore-transport` and delegates verification
and restoration to the branch's `.pixi-sandbox/tools/<platform>/pixi-sandbox`. When the config
cannot decide — no bundle covers this platform, or several do — it falls back to the branch
baked in at `init` time. Override branch selection only when needed:

<ContextChips chips={["airlock", "offline"]} />

```bash
PIXI_SANDBOX_BRANCH=sandbox/developer-linux-64 ./restore.sh  # exact branch
PIXI_SANDBOX_BUNDLE=developer ./restore.sh                   # pick among several bundles
```

See [Airlock Restore](/pixi-sandbox/restore/) for transfer options and the operator checklist.

## 6. Without cargo vendoring

Conda-only projects ship no crates at all. Set `cargo_vendor = false` on the bundle (or at the top
level), pack without `--cargo-vendor`, and the far side never sees a vendor tree. The full story —
what is vendored, how the restore wires `CARGO_HOME`, and the offline build proof — is in
[Cargo vendoring](/pixi-sandbox/guides/cargo-vendoring/).

## Init does not modify your Pixi manifest

`pixi-sandbox init` writes only the files it owns — the publisher workflow, the relock
workflow, the offline launcher, and `pixi-sandbox.toml` when it does not exist yet. Your
`pixi.toml` is left byte-identical: the CLI is installed globally with an explicit channel
(`pixi global install --channel https://prefix.dev/archont561/archont561 …`), which never
reads the project's channel list, and no generated file needs the project to know where the
CLI came from.

> **Upgrading from 0.4.3?** That release appended `https://prefix.dev/archont561` — the
> publisher's namespace root, which is a web page, not a channel — to
> `[workspace].channels`, so `pixi lock` failed with a 404 on any project with at least one
> dependency. Remove that entry from your `channels` array; nothing needs to replace it.

## Verification

`plan` prints exactly the matrix you intended, `doctor --verify` is green, and the remote carries
the orphan branch:

<ContextChips chips={["connected", "network"]} />

```bash
pixi-sandbox plan --config pixi-sandbox.toml --json
pixi-sandbox doctor --branch-location .sandbox-out --verify
git ls-remote origin 'sandbox/*'
```

## Failure modes

- **The sandbox branch is missing from the transfer** — entry 3 in
  [Troubleshooting and incident response](/pixi-sandbox/troubleshooting/): the bundle must carry
  both `main` and the sandbox branch.
- **A push is rejected for an oversized object** — entry 5; the shard limit and budgets are in
  [Transport sizes, sharding, and budgets](/pixi-sandbox/guides/sizes-and-budgets/).
- **The restore dies on a missing GUI, font, or display server** — entry 6; declare what the
  workload needs in `[host_requirements]` ([Host requirements](/pixi-sandbox/security/host-requirements/)).
