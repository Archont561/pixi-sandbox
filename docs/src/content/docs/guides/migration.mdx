The public composite Actions and the repository's reusable publisher were retired after native
packages became the canonical installation path. New refs do not contain the root, `setup`, or
`publish` Actions or the repository reusable workflow. Immutable older tags and commit SHAs remain
available for historical builds, so a pin you already have keeps resolving — nothing you merged
yesterday breaks today.

This page maps **every retired interface** to its replacement, with before/after commands, the
generated workflow changes the migration requires, and the ordered upgrade checklist.

## Native transport migration

Native transports replace environment pack/unpack helper processes with in-process rattler and
UV libraries. This requires a **breaking pre-1.0 minor release**, not a patch: scripts using the
removed helper interfaces must change. Version `0.7.0` predates the native interface; install a
release containing this migration before using the new flags below.

### Interface changes

| Previous interface or assumption | Native replacement |
|---|---|
| `tools list` / `tools update` and the helper catalogue | Removed; packing and format-1 restoration require no `pixi-pack` or `pixi-unpack` executable |
| `pack --fetch-tools`, `--tools-lock`, `--tools-cache` | Removed; delete these arguments, do not pass them through to another helper |
| Implicit Pixi/bootstrap bundling | Select local executables with `pack --pixi-bin PATH --self-bin PATH` when the airlock needs a self-contained launcher and Pixi commands |
| `wrap-payload --tools-cache` | Use the independent `wrap-payload --build-cache PATH`; `--build-tool PATH` chooses a local `rattler-build` for offline use |
| Previous source-build Rust floor | **Rust 1.94+**, edition 2024; prebuilt binaries do not require Rust on the consumer |
| Helper-driven packing | Read **Pixi lock version 7**; copy original SHA256-verified Conda archive/wheel bytes without solving or building dependencies |
| Arbitrary PyPI source dependencies | Lock compatible wheels; source archives, VCS dependencies and non-wheel project paths are refused before output creation (wheel-only input was already enforced in v0.7.0) |

`--pixi-bin` and `--self-bin` are independent optional selections. The bootstrap must be a
standalone executable, not a Pixi-managed trampoline. Omitting them is valid for a transport
consumed by an already installed CLI, but does not provide bundled Pixi or a self-bootstrap.
Selected executables retain byte-hash, size and linkage checks; tool budgets were not relaxed.
The `rattler-build` download is an independent optional payload-building feature, not a packing
or restore dependency.

### Transport compatibility

- New producers write **manifest schema 4**, with no implicit helper entries.
- Format-1 packs under manifest schemas **1, 2, 3 and 4** use native installation. The retained
  `pixi-pack.json` format marker is not a requirement for the `pixi-pack` binary.
- Older **opaque/non-format-1** transports retain their recorded legacy unpacker reader. Keep
  that legacy executable with the old transport where required; do not delete compatibility
  bytes from historical snapshots merely because new transports no longer need them.
- `unpack --unpacker PATH` remains an explicit external-executable override, not the default.
- New transports should be consumed with the matching new standalone bootstrap. Do not assume
  an older CLI understands schema 4. Retain an older snapshot for rollback.
- `restore` writes project markers and Cargo integration; `unpack` produces a raw prefix.
  Installation and staged per-file-oracle verification precede per-prefix rollback-protected promotion.
  Restoration is not an all-project transaction across environments, vendoring and registration.

### Native upgrade checklist

1. Install the new CLI on the connected producer. For a source build, use Rust 1.94 or newer.
2. Remove helper packages from your project's dependencies only if your own workload does not
   use them. Refresh the lock on a connected host and confirm it is version 7 with wheels for
   every selected PyPI dependency and target platform.
3. Remove retired helper-management arguments. Use the explicit local bundling flags if the
   disconnected consumer needs Pixi and the bootstrap. Regenerate owned workflows/launchers
   with the new `init`, then review and commit them; do not hand-edit version pins.
4. Pack a **fresh** output directory, verify it with `doctor --verify`, and inspect the manifest:
   schema 4, expected source commit, and only deliberately selected tool entries.
5. Test the new transport at a different destination on a network-denied consumer, including
   `doctor --verify-restored`, the frozen/offline Pixi check and the vendored Cargo build when
   applicable. Preserve the old snapshot until these checks succeed.

See [Create and verify a transport](/pixi-sandbox/reference/cli/create-verify/),
[Restore and inspect a transport](/pixi-sandbox/reference/cli/restore/), and
[Compatibility and releases](/pixi-sandbox/compatibility/) for exact flags and limitations.

## The migration matrix

| Retired interface | What it did | Replacement |
|---|---|---|
| Root composite Action | Whole-job entrypoint: toolchain setup plus publish in one call | The generated `.github/workflows/publish-sandbox.yml` |
| `setup` composite Action | Installed pixi and the pixi-sandbox CLI | `prefix-dev/setup-pixi` plus `pixi global install` from the ecosystem channel — both rendered into the generated workflow |
| `publish` composite Action | Packed, verified, and force-pushed the transport | The generated workflow's `pipeline` step: install, `pack`, `doctor --verify`, `publish` |
| Repository reusable publisher | A reusable workflow consumer repos called with `uses:` | The same generated, project-owned `publish-sandbox.yml` |

Nothing in the retired set has a successor that lives in this repository: the replacement is a
file your project owns and reviews.

## Before and after

### Before — a v0.3.x consumer workflow

Your workflow called one or more retired interfaces by pinned ref:

```yaml
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@...
      - uses: Archont561/pixi-sandbox@v0.3.0        # root composite Action (stale-ref-allowed)
      - uses: Archont561/pixi-sandbox/setup@v0.3.0   # setup composite Action (stale-ref-allowed)
      - uses: Archont561/pixi-sandbox/publish@v0.3.0 # publish composite Action (stale-ref-allowed)
      # or: uses: Archont561/pixi-sandbox/.github/workflows/<reusable>@v0.3.0 (stale-ref-allowed)
```

### After — one command set, on a connected host with Pixi installed

<ContextChips chips={["connected", "network"]} />

```bash
pixi global install --channel https://prefix.dev/archont561/archont561 --channel conda-forge pixi-sandbox
pixi-sandbox init
```

`init` writes `pixi-sandbox.toml`, the generated `.github/workflows/publish-sandbox.yml` and
`.github/workflows/relock.yml`, and this platform's `restore.sh` launcher. Review them and commit:

```bash
git add pixi-sandbox.toml .github/workflows/publish-sandbox.yml .github/workflows/relock.yml restore.sh
```

Delete the steps that called the retired interfaces — the generated file replaces them end to end.

## What the generated workflow gives you instead

Every capability the retired Actions carried has a named successor in the generated workflow:

| Retired capability | Where it lives now |
|---|---|
| Native publish matrix | `plan --json` feeds `strategy.matrix.include` — one job per bundle × platform |
| Checksum-verified toolchain | The "Fetch the pinned pixi-sandbox release" bootstrap verifies the standalone binary against the release's `SHA256SUMS` before execution |
| Verification gate | `doctor --verify` inside `pipeline`, budgets enforced before any push |
| Cargo vendoring | `--cargo-vendor` handed to `pipeline` from the plan matrix |
| Orphan-branch publish | `publish` inside `pipeline` — `<prefix>/<bundle>-<platform>`, force-push, `--keep` rotation |
| Upgrade lane | The generated workflow's own `upgrade` job proposes regenerated files as a pull request |

The full walkthrough is in [CI publishing](/pixi-sandbox/guides/ci-publishing/); the `[workflow]`
table that renders CI policy into the file is in
[Generated workflow policy](/pixi-sandbox/guides/workflow-policy/).

## Generated workflow changes — checklist

Work through this once, per consumer repository:

- [ ] `.github/workflows/publish-sandbox.yml` exists and is committed — generated, never hand-edited.
- [ ] Every step that called a retired Action (`uses: Archont561/pixi-sandbox...`) is deleted.
- [ ] The workflow pins `PIXI_SANDBOX_VERSION` to an exact release; no floating ref anywhere.
- [ ] `pixi-sandbox.toml` is committed next to the workflow — config is reviewed data.
- [ ] Customization that used to ride along in a retired Action's `with:` inputs now lives in the
      `[workflow]` table of `pixi-sandbox.toml`.
- [ ] Optional: the `PIXI_SANDBOX_UPGRADE_TOKEN` secret is added (Workflows-scoped) if you want the
      weekly upgrade lane to open its own pull requests.
- [ ] `actionlint` passes on the regenerated file.
- [ ] Historical jobs keep resolving their old immutable refs; nothing about the migration rewrites
      them.

## Upgrade checklist — the migration as a runbook

1. **Install the CLI** — the `pixi global install` command above, on a connected host.
2. **Generate** — `pixi-sandbox init`; read the plan output before accepting the writes.
3. **Review** — the generated workflow, the relock workflow, and `pixi-sandbox.toml`; adjust
   `[workflow]` policy rather than the file.
4. **Commit** — add the four generated paths in one commit, message noting the migration.
5. **Delete the old calls** — remove the retired `uses:` steps (or the reusable-workflow job).
6. **Push and verify** — the publish job runs `plan`, then one `pipeline` step per matrix entry;
   confirm the `publish-diagnostics-<platform>` artifact and the new orphan branch
   `sandbox/<bundle>-<platform>`.
7. **Hand over to the upgrade lane** — from the next release on, the `upgrade` job proposes
   regenerated files itself. Dispatch it with an exact version to migrate on demand:

<ContextChips chips={["ci", "network"]} />

```bash
gh workflow run .github/workflows/publish-sandbox.yml --ref main -f upgrade=X.Y.Z
```

## If you cannot migrate yet

An old pin is not an emergency: immutable tags and SHAs stay available for historical builds. What
you give up by waiting is the upgrade lane, the budgets gate, and reviewable generated files — the
[compatibility page](/pixi-sandbox/compatibility/) lists what each documented release supports.

## Verification

`actionlint` is clean on the regenerated file, the old `uses:` steps are gone, and the first push
runs the generated publisher to a green publish with the `publish-diagnostics-<platform>` artifact:

<ContextChips chips={["ci", "network"]} />

```bash
actionlint .github/workflows/publish-sandbox.yml
gh run list --workflow publish-sandbox.yml --limit 1
```

## Failure modes

- **A v0.4.3, v0.4.4, or v0.5.0 generated workflow fails with `curl: (22)`** — the download URL was
  built from the consumer's own repository; re-run `pixi-sandbox init --force` with a patched CLI
  (see [CI publishing](/pixi-sandbox/guides/ci-publishing/), issue #80).
- **The upgrade pull request is refused with a 403** — the token cannot write workflow files; the
  job stays green and uploads the `git apply`-able patch instead.
- **A publish leg fails after migrating** — the same failure surfaces as any generated publisher:
  [Diagnostics and evidence logs](/pixi-sandbox/security/diagnostics/) and
  [Troubleshooting and incident response](/pixi-sandbox/troubleshooting/).
