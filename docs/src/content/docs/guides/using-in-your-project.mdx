This guide is for **project owners** who want to ship their pixi environments to airlocked machines.

## The two product commands

Run the first command from the root of your Pixi project on the **connected side**:

```bash
curl -fsSL https://raw.githubusercontent.com/Archont561/pixi-sandbox/v0.3.0/scripts/init.sh | sh
```

The script detects Linux/macOS and CPU architecture, downloads the matching v0.3.0 release asset,
verifies it against the release's `SHA256SUMS`, and runs `pixi-sandbox init github`. It creates:

```text
.pixi-sandbox.toml
.github/workflows/publish-sandbox.yml
restore.sh
restore.ps1
```

Review and commit those files. Pushing the project runs the generated workflow and publishes the
configured `sandbox/<bundle>-<platform>` branches. Transfer Git history containing the project and
sandbox branch into the disconnected network. On the **airlock**, the second product command is:

```bash
./restore.sh
```

That script only uses local Git objects: it archives the platform's sandbox branch, locates the
verified nested binary, and restores everything offline. It never contacts GitHub. Windows users
run `.\\restore.ps1` instead.

> The Git push, workflow completion, and transfer across the air gap are deployment operations,
> not additional pixi-sandbox commands. The airlock clone must contain the sandbox branch.

### Select a release or mirror

The connected-side script accepts environment overrides:

```bash
PIXI_SANDBOX_VERSION=v0.3.0 \
PIXI_SANDBOX_REPOSITORY=Archont561/pixi-sandbox \
PIXI_SANDBOX_PROJECT_ROOT=. \
  sh -c "$(curl -fsSL https://raw.githubusercontent.com/Archont561/pixi-sandbox/v0.3.0/scripts/init.sh)"
```

## 1. Prerequisites

- Your project has `pixi.toml` + `pixi.lock`
- Optional: `Cargo.toml` + `Cargo.lock` if you want vendored crates
- On the connected host: `curl`, Git, and either `sha256sum` or `shasum`
- On the airlock: Git and `tar`; Pixi and `pixi-sandbox` do not need to be installed

The one-line initializer downloads `pixi-sandbox` temporarily and checksum-verifies it.

## 2. Decide what to ship

Not every env in `pixi.toml` should be an airlock branch. Declare explicitly in `.pixi-sandbox.toml`:

```toml
# .pixi-sandbox.toml
schema = 1
branch_prefix = "sandbox"
cargo_vendor = true  # false if you only need conda envs

[[bundle]]
name = "developer"
environments = ["dev", "docs"]
platforms = ["linux-64", "osx-arm64", "win-64"]

[[bundle]]
name = "minimal"
environments = ["default"]
platforms = ["linux-64"]
cargo_vendor = false
```

Validate:

```bash
pixi-sandbox plan --config .pixi-sandbox.toml
pixi-sandbox plan --config .pixi-sandbox.toml --json
```

This emits a GitHub Actions matrix — one job per `bundle × platform`.

## 3. Local pack → doctor → publish

<Tabs>
  <TabItem label="Rust self-bin (recommended)">
    ```bash
    # Build static self-binary
    cargo build -p pixi-sandbox --release

    # Pack
    pixi-sandbox pack \
      --repo-root . \
      --envs dev,docs \
      --output-dir .sandbox-out \
      --platform linux-64 \
      --cargo-vendor \
      --fetch-tools \
      --self-bin target/release/pixi-sandbox

    # Verify (writes nothing)
    pixi-sandbox doctor --branch-location .sandbox-out --verify

    # Publish
    pixi-sandbox publish \
      --input-dir .sandbox-out \
      --branch-name sandbox/developer-linux-64 \
      --remote origin
    ```
  </TabItem>
  <TabItem label="Release binary">
    ```bash
    # Download verified release
    # (use setup action in CI, or manual curl + sha256sum check)

    pixi-sandbox pack \
      --repo-root . \
      --envs dev \
      --output-dir .sandbox-out \
      --platform linux-64 \
      --fetch-tools \
      --self-bin ./pixi-sandbox-x86_64-unknown-linux-musl
    ```

## 4. What gets published?

```text
sandbox/developer-linux-64 (orphan branch)
├── .pixi-sandbox/
│   ├── manifest.json              # SHA-256 catalog, source commit, tool versions
│   ├── envs/dev/pack/             # pixi-pack --directory-only output
│   │   ├── channel/linux-64/*.conda
│   │   ├── environment.yml
│   │   └── pixi-pack.json
│   ├── envs/docs/pack/            # second env, shared .conda files deduped by git
│   ├── tools/linux-64/            # pixi, pixi-unpack, pixi-sandbox (static, verified)
│   └── vendor/                    # cargo vendor --versioned-dirs (if enabled)
├── README.md                      # human restore instructions
└── AGENTS.md                      # agent instructions
```

Sizes (measured small project, 2 envs, 33 crates, linux-64):

| Part | Size |
|------|------|
| conda envs (.conda) | 133 MB |
| cargo vendor (loose) | 33 MB |
| tools (pixi, pixi-unpack, self) | 96 MB |
| **transport dir** | **262 MB** |
| **orphan branch after git dedup** | **~110 MB** |

Tools dominate small bundles — expected, git stores each tool blob once.

## 5. Restore on airlock

After the project and its sandbox branch have crossed the air gap:

```bash
./restore.sh
```

The generated script selects the native platform branch, uses `git archive` into
`.pixi/.restore-transport`, and delegates verification and restoration to the branch's
`.pixi-sandbox/tools/<platform>/pixi-sandbox`. Override branch selection only when needed:

```bash
PIXI_SANDBOX_BRANCH=sandbox/developer-linux-64 ./restore.sh
```

See [Airlock Restore](/pixi-sandbox/restore/) for transfer options and the operator checklist.

## 6. Without cargo vendoring

If you only need conda envs:

```toml
# .pixi-sandbox.toml
schema = 1
cargo_vendor = false

[[bundle]]
name = "python"
environments = ["dev", "test"]
platforms = ["linux-64", "win-64"]
```

And pack without `--cargo-vendor`:

```bash
pixi-sandbox pack --repo-root . --envs dev --output-dir .sandbox-out --platform linux-64 --fetch-tools --self-bin target/release/pixi-sandbox
```
