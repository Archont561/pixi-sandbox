This page is the lifecycle surface: which release these docs describe, what the tool supports, how
to upgrade, and what happens to the files a previous release generated. Every page's footer names
the same documented release.

## Documented release

The version in the footer is resolved from the tree these docs were built from — never restated by
hand — so it cannot rot against a release. Release notes and the full history:

## Support matrix

| Component | Requirement | Notes |
|---|---|---|
| **pixi-sandbox** | the documented release (`__VERSION__`) | Static standalone binaries; no runtime dependencies |
| **Pixi platforms** | `linux-64`, `linux-aarch64`, `osx-64`, `osx-arm64`, `win-64` | The platforms the embedded tool pins cover; `plan` rejects a platform without pins |
| **Release assets** | `pixi-sandbox-x86_64-unknown-linux-musl`, `-aarch64-unknown-linux-musl`, `-x86_64-apple-darwin`, `-aarch64-apple-darwin`, `-x86_64-pc-windows-msvc.exe` + `SHA256SUMS` | The verified bootstrap paths |
| **Connected host** | Pixi (recent), Git, network to prefix.dev and GitHub | Pixi drives `pack`; the generated workflow can pin `setup-pixi`'s version via `[workflow].pixi_version` |
| **Airlock** | Git and `tar`; **no network** | Pixi and pixi-sandbox do not need to be pre-installed — the restore registers both from the transport |
| **Building from source** | Rust 1.88+ (workspace MSRV), edition 2024 | `cargo build -p pixi-sandbox --release` |
| **Config schema** | `schema = 1` | Readers refuse a newer schema; an older config is accepted silently and reported by `init --check` |
| **Generated workflow** | rendered by the release that wrote it | Every generated file carries a `pixi-sandbox-version` marker; see the upgrade policy below |

The exact helper-tool pins a release embeds (`pixi`, `pixi-pack`, `pixi-unpack`) are reviewed data:
`pixi-sandbox tools list` prints them, and `tools update --check` reports staleness without
downloading anything.

## Upgrade checklist

1. **Update the CLI** — `pixi global install --channel https://prefix.dev/archont561/archont561
   --channel conda-forge pixi-sandbox`, or `pixi-sandbox self-update --version X.Y.Z` for a
   standalone binary (never `latest` in a committed workflow or transport).
2. **Audit the tree** — `pixi-sandbox init --check` renders every owned file fresh, writes nothing,
   and names each finding (missing / stale / foreign / unsupported schema) with its remedy.
3. **Regenerate** — `pixi-sandbox init` (add `--force` only for a foreign file at an owned path),
   then review the diff: the output always matches what the config describes.
4. **Land it** — commit and push. A `GITHUB_TOKEN` push starts no `on: push` workflow, so dispatch
   the publisher explicitly: `gh workflow run .github/workflows/publish-sandbox.yml --ref main`.
5. **Republish the transport** — the next publish records the new tool versions in the manifest.
6. **Re-restore the airlock** — transfer the new branch and run `./restore.sh`; verification and
   the offline assertions must stay green.

## Generated-workflow upgrade policy

A new release leaves every consumer's generated files stale until something notices. The generated
publisher closes that gap without ever floating a production pin:

- **Weekly, on its own** — the `upgrade` job bootstraps the standalone binary the workflow is
  currently pinned to, asks that exact binary to `self-update` to the latest release, and runs
  `init --check` with it.
- **On demand** — `workflow_dispatch` names an exact version to propose (which is also the
  rollback path).
- **Drift becomes a pull request** — when `init --check` finds drift, the job re-runs `init` and
  opens a PR containing only the regenerated files. It **never pushes to `main` and never touches
  `pixi-sandbox.toml`**; config is reviewed data, and a schema the updated binary no longer
  understands is reported as a finding for a human.
- **Pins never float** — `latest` only ever decides what the *proposed* PR contains; every
  committed workflow and published transport names an exact release.
- **Without the optional token** — the job stays green, writes an actionable error, and uploads a
  `git apply`-able patch so a maintainer can apply the upgrade manually.

## Retired interfaces

The public composite Actions and the repository reusable publisher were retired when native
packages became the canonical installation path. Immutable old tags remain for historical builds.
The before/after mapping and the migration checklist are in
[Migration from composite Actions](/pixi-sandbox/guides/migration/):

| Retired interface | Replacement |
|---|---|
| Repository `setup` composite Action | `pixi global install` from the ecosystem channel (in the generated workflow) |
| Repository `publish` composite Action | direct `pixi-sandbox pack` / `doctor --verify` / `publish` calls |
| Repository reusable publisher workflow | the generated, project-owned `publish-sandbox.yml` |

## Versioning policy

Before 1.0, a breaking change advances the minor version. This site documents the current release
only — a version switcher arrives when several documentation versions are actively maintained, not
before.
