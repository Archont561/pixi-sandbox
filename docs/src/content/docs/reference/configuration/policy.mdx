**Use this when** you need the complete field tables for the policy sections of
`pixi-sandbox.toml`: what ships (`[[bundle]]`), what it may cost (`[budgets]`), where it builds
(`[runners]`), how the publisher behaves (`[workflow]`), and what the host must provide
(`[host_requirements]`). File location, schema, and top-level fields are in
[Configuration overview](/pixi-sandbox/reference/configuration/overview/).

## `[[bundle]]`

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | yes | Bundle name, used in branch: `sandbox/<name>-<platform>` |
| `environments` | string[] | yes | Explicit pixi envs — never inferred from `pixi.toml` |
| `platforms` | string[] | yes | Platforms to publish (e.g., `linux-64`, `osx-arm64`) |
| `cargo_vendor` | bool | no | Override top-level `cargo_vendor` |

Emitted branches for the example configuration:

```text
sandbox/developer-linux-64
sandbox/developer-osx-arm64
sandbox/developer-win-64
sandbox/minimal-linux-64
```

## `[budgets]` — pre-publish size ceilings

Optional, within schema 1. Missing fields use the defaults below; `pixi-sandbox init` writes the
same values explicitly for new projects. The generated publisher runs `doctor --verify
--budget-config <config>` after `pack` and before `publish`, so an over-budget transport fails
without replacing the last healthy orphan branch.

| Field | Type | Default | Measures | Remedy |
|-------|------|---------|----------|--------|
| `max_blob_mib` | float | `95` | Largest stored Git object: an unsplit blob, split part, embedded tool, or oracle file | Lower `--shard-limit-mib` or remove the single oversized payload. This value cannot exceed `95`. |
| `max_transport_mib` | float | `2048` | Declared bytes verified by `doctor`: env pack blobs, file-oracle blobs, tools, and vendored Cargo blobs | Split the reviewed environment set into separate `[[bundle]]` entries. |
| `max_repository_push_mib` | float | `2048` | File bytes staged into the orphan snapshot before Git compression | Split the reviewed environment set into separate `[[bundle]]` entries. |
| `max_restore_required_mib` | float | `8192` | Restore preflight estimate: packed + unpacked env bytes plus two vendor copies | Split the reviewed environment set into separate `[[bundle]]` entries. |

Budgets do not change the transport format. If a bundle grows past a ceiling, keep each branch
self-contained by publishing fewer environments per `[[bundle]]`; do not split a single
environment or move payloads outside the transport. The measured numbers and the sharding
mechanism are in [Transport sizes, sharding, and budgets](/pixi-sandbox/guides/sizes-and-budgets/).

## Runners

| Platform | Default runner | Notes |
|----------|----------------|-------|
| `linux-64` | `ubuntu-latest` | Hosted |
| `linux-aarch64` | **none** — must provide `[runners]` | No safe hosted default, require self-hosted |
| `osx-64` | `macos-15-intel` | Hosted Intel |
| `osx-arm64` | `macos-14` | Hosted Apple Silicon |
| `win-64` | `windows-latest` | Hosted |

Rules enforced by `plan`:

- Runner label cannot contain control chars or outer whitespace
- Every `[runners]` entry must be used by at least one bundle (stale typo = error)
- Platform must be one of the supported native platform mappings; unsupported platforms are refused. No helper catalogue or per-helper pins are required.

## `[workflow]` — generated-publisher CI policy

Optional, within schema 1. Every real repository wants to change a handful of the generated
`publish-sandbox.yml`'s defaults (the push trigger, token permissions, concurrency, job timeouts,
the pixi pin and its cache). Before this table existed, those were hand edits a consumer
re-applied by ritual every time `init --force` regenerated the file, with nothing confirming the
re-applied edit still matched what the current generator would have produced. Carrying the same
policy in config instead means `init` reproduces the consumer's exact workflow with **no hand
edits at all** — run `init` again any time, including from the scheduled upgrade job, and the
output never drifts from what the table describes.

No `[workflow]` table at all renders byte-identically to the historical, pre-policy template —
existing projects need no changes. Once the table is present **at all**, even empty, three fields
move to a safer default unless given an explicit value: `setup_pixi_cache` defaults to `false`,
`push_paths` defaults to a derivation instead of the unfiltered trigger, and `relock_paths`
defaults to a derivation that includes manifests + lockfiles (TASK-121). The other fields stay
fully opt-in per key.

```toml
[workflow]
push_paths = ["pixi-sandbox.toml", "pixi.toml", "pixi.lock"]  # optional, see below
relock_paths = ["pixi.toml", "pixi.lock", "Cargo.toml", "Cargo.lock"]  # optional, see below
permissions = true            # optional, default false
pixi_version = "0.81.0"       # optional, default unset (setup-pixi resolves its own default)
setup_pixi_cache = true       # optional, default false once [workflow] is present at all

[workflow.concurrency]        # optional
group = "publish-sandbox"
cancel_in_progress = false    # optional, default false

[workflow.timeouts]           # optional
plan = 15
publish = 60
```

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `push_paths` | string[] | derived (see below) once `[workflow]` is present; otherwise no filter | `on.push.paths:` allowlist for publish workflow. A plain entry is a path; a `!`-prefixed entry is GitHub's negation syntax. No `..` component or leading `/`. |
| `relock_paths` | string[] | derived (see below) once `[workflow]` is present; otherwise no filter | `on.pull_request.paths:` allowlist for relock workflow (TASK-121). Safe default includes manifests + lockfiles so hand-edited or deleted locks are still caught. No `..` component or leading `/`. |
| `permissions` | bool | `false` | When `true`, the workflow-level `permissions:` becomes `contents: read` and only the `publish` job regains `contents: write`, scoped to the job that needs it. `false` keeps the historical unconditional top-level `contents: write`. |
| `concurrency.group` | string | `publish-sandbox-${{ github.repository }}` | `concurrency: { group: ... }` for the whole workflow — prevents two publishes racing to force-push the same orphan branch. Repository-wide grouping, `cancel-in-progress: false` by default. |
| `concurrency.cancel_in_progress` | bool | `false` | Paired with `concurrency.group`. `false` prevents aborting a running publish mid-flight; GitHub still cancels a superseded pending run (at most one running + one pending). |
| `timeouts.plan` | int (minutes) | unset | `timeout-minutes:` on the `plan` job. |
| `timeouts.publish` | int (minutes) | unset | `timeout-minutes:` on the `publish` job — a hung `pack` should not hold a runner for the six-hour default. |
| `pixi_version` | string | unset | Pins `setup-pixi`'s own `pixi-version:` input on every `setup-pixi` step. |
| `setup_pixi_cache` | bool | `false` once `[workflow]` is present, otherwise unset (no `cache:` key at all) | `setup-pixi`'s `cache:` input. pixi-sandbox owns the native `pixi install` while packing; a cache keyed on the consumer manifest can restore a solve the pack will not reuse — a correctness hazard, not mere staleness. Set `true` explicitly to keep the old best-effort caching. |

### `push_paths` and `relock_paths` derivation

Unset, once `[workflow]` is present, `init` derives the allowlists from the transport inputs `plan`
already depends on:

- `push_paths`: the sandbox config itself, `pixi.toml`, `pixi.lock` (always), plus whichever of
  `package.json`, `bun.lock`, `Cargo.toml`, `Cargo.lock` actually exist in the project.
- `relock_paths`: same as `push_paths` but includes lockfiles unconditionally (`pixi.lock`,
  `Cargo.lock` always) plus `**/Cargo.toml` (workspace members) and `.cargo/config.toml` when
  present — the safe default that still catches hand-edited or deleted locks (TASK-121).

`pixi-sandbox plan --config pixi-sandbox.toml --json` surfaces the derived `push_paths` under its
own key, so a consumer can diff what the next `init` would write before running it. An explicit
`push_paths` or `relock_paths` always overrides its derivation.

The narrative version — why policy lives in config at all — is in
[Generated workflow policy](/pixi-sandbox/guides/workflow-policy/).

## `[host_requirements]` — host-level declarations

Optional, within schema 1. A restored transport is a complete Pixi environment; it is not a
complete machine. Fonts, an X server, D-Bus, GPU access and the C runtime come from the host, so a
GUI workload can fail *after* a restore that verified perfectly — the failure mode
[issue #109](https://github.com/Archont561/pixi-sandbox/issues/109) describes. This table is where
a project declares those expectations.

It is deliberately named `host_requirements` rather than pixi's `system-requirements`: pixi's
table constrains the *conda solver* (it declares virtual packages such as `__glibc` that builds
are selected against), while everything here is host state. Nothing in the table is ever installed
into the environment — pixi-sandbox does not bundle display servers, GPU drivers or OS services,
and the boundary is the point: the declaration exists so a missing host dependency is named before
the application is launched instead of after.

Declarations are shared by default and refined per host family — `linux`, `osx` and `windows`, the
families the five Pixi platforms map to (`linux-64` and `linux-aarch64` → `linux`,
`osx-64`/`osx-arm64` → `osx`, `win-64` → `windows`).

```toml
[host_requirements]
libc = ">=2.34"                    # optional floor: "2.34" is the same statement
packages = ["fontconfig"]          # host packages required on every family
services = ["dbus"]                # host services that must be available
capabilities = ["display"]         # closed set: display, gpu
headless = ["xvfb-run"]            # any one of these satisfies a display requirement

[host_requirements.linux]          # optional: adds to the shared entries, wins on libc
packages = ["fontconfig", "fonts-dejavu", "xvfb"]
```

| Field | Type | Description |
|-------|------|-------------|
| `libc` | string | Minimum C runtime, `major.minor` or `major.minor.patch`, with an optional `>=` prefix; only a minimum is accepted. Linux-only: the `osx` and `windows` sections refuse it. |
| `packages` | string[] | Host packages (distro-level) the workload needs. Single names without whitespace. |
| `services` | string[] | Host services that must be available, for example a D-Bus session bus. |
| `capabilities` | string[] | Closed set: `display`, `gpu`. A value outside it is a config error, not a silently skipped check. |
| `headless` | string[] | Programs on `PATH`, any *one* of which satisfies a display requirement when there is no physical display (`xvfb-run` is the canonical entry). |
| `linux`, `osx`, `windows` | tables | Per-family additions and overrides. A family's `libc` replaces the shared floor; the lists accumulate. |

Resolution is the one rule to remember: shared entries always apply, a family's section adds to
them (duplicates are dropped, declaration order kept), and a section cannot remove a shared entry.
To require something on a single family, declare it in that family's section alone.

Validated at load, each with a named error: an unknown capability or family section, a malformed
`libc` floor, a duplicated entry, an entry containing whitespace, and an empty table or empty
family section (a table that declares nothing is a typo, not a declaration).

**Status.** The declaration is validated whenever a config is loaded, `pack --config` records the
set resolved for the packed platform in the transport's `manifest.json` (additive, so a transport
without the section is byte-identical to what earlier releases packed and restores exactly as
before), and `doctor` classifies it against the host it runs on — satisfied, missing, unknown or
not applicable — with per-distribution install guidance and a JSON report a CI job can branch on.
Enforcement stays opt-in (`doctor --require-host-requirements`). See the
[CLI reference](/pixi-sandbox/reference/cli/create-verify/#doctor) for the probes and the exit-code
contract and [Host and GUI requirements](/pixi-sandbox/security/host-requirements/) for a worked
Tauri-style example and the boundary that nothing is installed or granted.

## Full examples

### Full (multi-env, multi-platform, cargo)

```toml
schema = 1
branch_prefix = "sandbox"
cargo_vendor = true

[runners]
linux-aarch64 = "self-hosted-arm64"

[[bundle]]
name = "developer"
environments = ["dev", "docs"]
platforms = ["linux-64", "linux-aarch64", "osx-arm64", "win-64"]

[[bundle]]
name = "ci"
environments = ["default"]
platforms = ["linux-64"]
cargo_vendor = false
```

### Self-hosted override

```toml
schema = 1

[runners]
linux-64 = "my-large-runner"
osx-arm64 = "self-hosted-mac"

[[bundle]]
name = "prod"
environments = ["prod"]
platforms = ["linux-64", "osx-arm64"]
```
