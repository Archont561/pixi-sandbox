## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-88 taught ADR-13's per-file oracle that `*.dist-info/uv_cache.json` and the `RECORD` row that
hashes it are regenerated by a `pixi-unpack` reinstall. A real connected-host round trip
(2026-10-11, released v0.6.1, `python 3.12` + pypi `six`) showed there is a **third** such file:
`*.dist-info/direct_url.json`. uv records the *local wheel path* it installed from
(`file://…/pypi/six-1.17.0-py2.py3-none-any.whl`), so the file's bytes differ between the
pack-time verification unpack and the restore-time unpack, and `RECORD` hashes that file
verbatim, so its `RECORD` row differs too.

The oracle already canonicalises the path *inside* `direct_url.json` (its own entry verifies),
but `RECORD` embeds the sha256 of the un-canonicalised bytes, which cannot be canonicalised by
string replacement. The result: `restore` still exits non-zero with
`the restored project does not match the manifest (1 failure(s))` on the package's `RECORD`,
exactly the deterministic failure issue #128 describes. Because `pixi-unpack` installs pypi
dependencies from a local wheel for every package, this is not `six`-specific: **every packed
transport containing a pypi wheel still fails #128**, including on current `main`
(`files_manifest.rs` is byte-identical to v0.6.1).

This is the gap TASK-88 AC#8 exists to catch. It was carried open; this task is its home.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Found during the TASK-88 AC#8 verification session. Evidence, commands and the RECORD diff that
isolates this file are recorded in TASK-88's notes.

### 2026-10-11 — local implementation

`UV_INSTALL_METADATA` is now the single list of uv-regenerated files:
`uv_cache.json` and `direct_url.json`. `scan_prefix` consequently records both as
presence-only, `is_allowed_extra` accepts either when an older or different uv did not list it,
and the `canonical_file_sha256` path shared by pack and verify collapses the matching `RECORD`
rows. All other `RECORD` rows remain digested.

AC#2 is held by a same-basename-outside-`.dist-info` digest test. AC#3 adds a `verify_restored`
fixture whose pack-time and restore-time `direct_url.json` values name different local wheels;
the existing package-payload-tampering complement still reports an integrity failure.

TDD evidence: each new behavioural probe failed with the production extension neutralised, then
passed with it restored — `a_regenerated_direct_url_row_does_not_change_a_record_digest`,
`direct_url_json_is_recorded_without_a_digest`, and
`a_uv_reinstalled_pypi_environment_matches_the_oracle`. ADR-21 now records the two-file rule and
its limits. No `files.json` schema change was needed.

**AC#4 remains open.** This airlocked host cannot run the required real `pixi-pack` →
`pixi-unpack` pypi-wheel round trip because it cannot resolve against `prefix.dev`. The local
fixture proves the seam but is not substituted for connected-host evidence.

### 2026-10-15 — AC#4 satisfied on a connected host

The full evidence (commands, versions, oracle entries, restore output and the v0.6.1 red / v0.6.2
green comparison) is recorded once, in TASK-88 § Implementation Notes, because the two ACs name
the same connected round trip. Summary: a `python 3.12` + pypi `six 1.17.0` project was packed
with the fixed build (`pixi-pack 0.7.11`, 6416 file entries) and restored with the embedded
`pixi-unpack 0.7.11`; the restored `direct_url.json` carries the restore-time local wheel path,
and the restored tree verified with **0 failure(s)** (exit 0). The pre-fix v0.6.1 binary failed
the same transport on `six-1.17.0.dist-info/RECORD` with the issue-#128 signature; the released
v0.6.2 (which contains the fix) and the local main build both pass. `direct_url.json` and
`uv_cache.json` are recorded presence-only in the manifest, and the `RECORD` row that hashes
`direct_url.json` is collapsed to the shared sentinel — exactly the TASK-93 change.

## Final Summary

<!-- SECTION:SUMMARY:BEGIN -->
`*.dist-info/direct_url.json` is now modelled like `uv_cache.json`: presence-only in the
per-file oracle, with its `RECORD` row collapsed to `@pixi-sandbox-regenerated@` through the one
shared `canonical_file_sha256` entry point, so pack and verify cannot drift. Because
`pixi-unpack` always reinstalls a pypi dependency from a local wheel, `direct_url.json` names a
different path on every host and prefix, and `RECORD` embeds that path's hash — the file issue
#128 could not survive. Exercised against a real `pixi-pack` → `pixi-unpack` round trip of pypi
`six 1.17.0` on a connected host: the restored tree verifies with 0 failures with the fix, and
fails on `six-1.17.0.dist-info/RECORD` with the pre-fix v0.6.1 binary. Files merely named
`direct_url.json` outside a `.dist-info`, and tinkering with the payload the wheel shipped, are
still caught.
<!-- SECTION:SUMMARY:END -->
