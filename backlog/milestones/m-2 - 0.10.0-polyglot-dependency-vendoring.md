title: "0.10.0 — Polyglot dependency vendoring in one transport"

## Description and exit criteria

A polyglot repository's non-Cargo dependencies — Go modules, NuGet packages and Maven
artifacts — pack into the same self-contained transport as its Conda environments and Cargo
crates, and the restored project builds against them with the network namespace denying all
egress. Each provider is opt-in and lockfile-driven: no automatic scanning, no blanket
downloads, and an unsupported or incomplete dependency graph fails on the connected host
before a byte is packed. Existing Cargo vendoring and Conda-only bundles keep their current
behaviour (TASK-130 non-goal: nothing existing changes shape).

Exit criteria:

1. The TASK-130 spike is timeboxed and produces evidence, not product: for each ecosystem the
   lockfile/manifest inputs, the offline-wiring mechanism and the failure mode of an
   incomplete graph are written into the task notes (and an ADR amendment where the transport
   layout changes). Go first because `go mod vendor` is a native, lockfile-driven mechanism;
   Maven last because it has no standard lockfile.
2. At least the Go provider ships end to end: reviewed config surface, per-workspace
   transport placement consistent with ADR-33's per-workspace model, content-hash
   verification on restore, and an ignored `unshare -n` offline build proof with a cold
   negative control, in the same shape as `test-vendor-offline` and wired as a changes-gated
   CI step. NuGet and Maven may follow in the same sprint or be explicitly deferred with
   recorded reasons; the opt-in contract for the deferred providers is designed, not shipped
   half-working.
3. The airlock gate is green on the release branch at the sprint's end. The m-1 ruling on
   criterion 3 (namespace gates as the nesting evidence) applies per ecosystem here too; any
   new provider's offline proof is a real-runner gate, never a hand-built fixture claim.
4. The release gate task for m-2 exists on the board before the sprint's release stage
   starts (doc-18 §5.3; the m-1 gap that TASK-136 closed must not recur), its criteria are
   checked with run-id evidence, and `v0.10.0` is published by `release.yml` (five static
   binaries, five conda packages, `SHA256SUMS`).

## Sprint train

One spike-first sprint, same four-stage shape as m-1:

- **Stage A — spike (TASK-130).** Go module vendor mechanics against `go.mod`/`go.sum`,
  including how a vendored module tree is verified and how `go build -mod=vendor` behaves in
  a denied namespace; the NuGet locked-restore-into-a-local-source design; and the Maven
  problem statement (no lockfile: explicit artifact lists plus integrity checks). Output is
  evidence and the config/transport design, including whether ADR-33's per-workspace tree
  model extends unchanged or needs an ADR-34.
- **Stage B — build.** Providers in the spike's order, each its own focused PR, behind
  opt-in config that leaves every existing bundle byte-identical when unused.
- **Stage C — gate.** Per-provider ignored offline proofs on real runners, the full suite
  holding or rising, fmt/lint green, and the release-branch airlock decision reconfirmed.
- **Stage D — release.** Create the m-2 release-gate task first, then the version cut. The
  m-1 release used the human-pushed `milestone-v*` tag lane (no release PR, bot commit
  straight to main); whether m-2 repeats that lane or returns to a reviewed release PR is an
  explicit decision recorded in the gate task, not an accident.

Out of this milestone: any ecosystem beyond Go, NuGet and Maven; changes to the Cargo
vendor contract (ADR-6/ADR-33 stay in force unless the spike proves an amendment); the
airlock harness extension m-1's ruling deferred, which remains a documented accepted risk
until the publish/fetch plumbing around workspaces actually changes.

## Version policy

Same pre-1.0 policy as m-1: a breaking transport or manifest change is a **minor** bump, so
the target is `0.10.0` even though the features are additive; package versions and transport
schema versions stay independent, and manifests are not bumped while planning. A suffix
(`0.10.0-rc.1`) remains available and makes `release.yml` dry-run the registries. 1.0.0 still
needs its own explicit stability decision and is not a planning default.

## Release gate

The milestone is closed by its release-gate task, never by an assertion or a merge (the m-1
rule, now exercised once: TASK-136 owned the v0.9.0 cut end to end). The m-2 gate task is
created at Stage D entry and carries the same evidence DoD — run ids for every box, recorded
sanction for every human-gated action, a red leg keeps the task open with its run id — plus
whatever the m-1 post-release watch (the scheduled two-tier airlock on the release commit)
teaches about ordering the gate before publication.
