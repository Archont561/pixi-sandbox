## Description and exit criteria

A repository with explicitly declared nested Pixi workspaces packs to **one** transport and
restores on an airlock as a single, verifiable tree: every declared workspace's environments,
its Cargo vendor tree and its tools come from the same manifest, and the airlock gate proves
the restored workspace set — not only the root one.

Exit criteria:

1. TASK-129 is closed: the nested transport is packed, restored and verified on a transport
   whose lockfile pixi itself generated (its one remaining obstacle, AC#7).
2. TASK-131 is closed: per-workspace Cargo vendor trees travel in the same transport and the
   restored tree wires each workspace to its own tree.
3. The airlock gate — `airlock linux-64`, both tiers — is green on the release branch, with the
   nested workspace present in the proof transport, not only in a fixture. **Amended by the
   2026-10-25 owner ruling below; the literal proof-transport clause is discharged by the two
   runner-executed namespace gates.**
4. The release gate task's acceptance criteria are checked and `v0.9.0` is published by
   `release.yml` (five static binaries, conda packages, `SHA256SUMS`).

### Ruling on criterion 3 — 2026-10-25 (owner-selected, recorded in TASK-136)

**Why the literal reading cannot hold as written.** The airlock proof packs this repository
using its schema-1 `.pixi-sandbox.toml`, which declares one bundle and no nested workspaces; the
harness has no project/config override input, so no nested workspace can appear in that proof
transport without harness work of its own. The criterion's actual intent was to stop the
milestone closing over *hand-built-lock hermetic fixtures* — the `nested_workspaces` tests that
drive a fake cargo wrapper and locks pixi itself refuses to load.

**Evidence that discharges that intent — real toolchains on GitHub runners, not fixtures.**
Two changes-gated `ci.yml` proofs execute the full nested lifecycle inside a fresh
`unshare -n` network namespace with isolated HOME and caches:

- `test-nested-offline` (TASK-129, PR #209): pixi itself solves both projects against a local
  `file://` channel and writes genuine v7 locks; the product packs the nested pair, restores
  into a clean consumer, proves `pixi install --frozen --offline` a no-op by payload hash and
  the delegated nested task executes the packaged payload; a cold negative control fails.
  Runner evidence: run `40144185678` (TASK-129 ledger), re-green in run `40198959531`.
- `test-vendor-offline` (TASK-131, PR #211): two distinct `Cargo.lock` files with real crates.io
  crates (`itoa`, `memchr`), real `cargo vendor` output, two per-workspace vendor trees in one
  transport, both projects building `cargo build --offline` against their own restored sandbox
  `CARGO_HOME` inside the namespace, binaries proving the crates linked, plus a cold negative
  control that fails 101 with the vendor tree removed. Runner evidence: run `40198959531`,
  step `Run pixi run test-vendor-offline` success.

**What the airlock uniquely proves, and why it is workspace-agnostic.** The airlock's
distinctive machinery is the released-binary self-bootstrap, the throwaway orphan-branch
publish and developer-shaped fetch, the two-tier `ci_gate` restore replay, and the scheduled
offline cargo compile. None of those paths branch on workspace nesting; the nesting-specific
behaviour — schema-5 manifests, per-workspace pack trees, per-tree verification and per-project
cargo wiring — is exactly what the two namespace gates exercise end to end. The release branch
still needs its green full two-tier airlock (TASK-136 AC#4) as general transport-health
evidence; this ruling only settles what must be *inside* that proof.

**Residual risk, accepted explicitly.** No transport containing a nested workspace has yet
been packed with the *released* binary and cycled through publish/fetch. If a later release
changes the publish, fetch or restore plumbing around workspaces, this ruling is revisited and
a harness extension (the rejected option in the 2026-10-25 decision) becomes release-blocking
work rather than a recorded boundary.

## Version policy

0.9.0 is a SemVer planning target and is not published until the release gate cuts it. This
project is pre-1.0: a breaking transport or manifest change is a **minor** bump (0.8.0 → 0.9.0),
fixes are patches, and prereleases may use a suffix (`0.9.0-rc.1`) — a suffix makes `release.yml`
dry-run the registries instead of publishing. Package versions and transport schema versions are
independent; do not bump manifests while planning. 1.0.0 needs its own explicit stability
decision and is not a planning default.
